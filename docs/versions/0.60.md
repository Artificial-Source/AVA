# AVA 0.60 Backend Platform Catch-Up

AVA 0.60 is the historical documentation release-position line for backend platform catch-up. It exists because the old 0.33 ledger became a long slice-by-slice history while the actual backend moved across several roadmap phases.

The runtime number was restored to `0.32.0` after the May backend bump. This is not a stable release. The terminal frontend is still in active development. This document remains historical evidence for the platform catch-up line, not current runtime guidance.

## Why 0.60

- 0.32 shipped the ncursesw TUI replacement baseline.
- 0.33 started as backend maturity tracking, then accumulated more than one release worth of backend hardening, protocol work, provider work, tool work, and extension seams.
- Backend work is no longer just a 0.33 cleanup line: Phases 0-4 are closed for the approved scope, Phase 5 has a verified foundation, 0.65/0.70 cover provider/reasoning hardening with offline/fake validation, and 0.75 carries the implemented plugin/MCP foundation.
- Using 0.60 keeps the version docs aligned with roadmap phase progress without claiming Backend 1.0/MVP is complete.

## Current Roadmap Position

- Phase 0: closed. Product/version docs now surface the backend capabilities that used to be under-reported.
- Phase 1: closed for the current scope. Auth refresh, permission audit persistence, atomic writes, baseline safety checks, and headless basics are implemented.
- Phase 2: closed for the approved scope. Runtime events, protocol envelopes, RPC versioning, cancellation, resolver replies, and queue lifecycle flows exist.
- Phase 3: closed for the approved core scope. Context loading, manual and automatic compaction, usage/cost records, session stats, additive session versioning, and branching-ready ids exist.
- Phase 4: closed for the core tool-quality scope. Search, edit/diff diagnostics, webfetch, LSP diagnostics, process/tool bounds, and line-first output windows are implemented or have focused foundations.
- Phase 5: foundation-complete, not release-complete. Provider registry, model catalog, provider-neutral auth paths, retry/error normalization, model-change entries, and RPC model listing/switching exist.
- Phase 5.5: offline/fake coverage is in place for Anthropic native content/tool replay, Kimi/Moonshot/OpenAI-compatible profile foundations, reasoning/session shape work, provider-switch safety, and retry/idempotency documentation. Live credentialed endpoint smokes and broader provider drift checks remain release-validation work.
- Phase 6: 0.75 extension foundation is source-backed. Plugin/MCP subprocess containment, command exposure, MCP prompt discovery/invocation, unified command-registry seams, authoring docs, a checked-in sample plugin, compatibility policy, minimal golden contracts, focused audit rechecks, selected failure coverage, and the then-current MCP resource deferral decision are implemented; read-style MCP resources later landed behind `mcp.resource.read`, while broader release validation and final failure-matrix closure continue through later version docs.

## Backend Capability Themes

- Semantic backend/frontend boundary: runtime events and command results carry typed semantic data rather than terminal layout instructions.
- Headless maturity: print and JSONL RPC expose provider streaming, permission/question replies, command execution, session state, compaction, cancellation, steering, follow-ups, and model/session operations.
- Session durability: append-only JSONL entries, compaction records, permission audit entries, usage/cost stats, model-change records, validation, and branching-ready ids are in place.
- Tool hardening: file/search/bash/apply_patch/webfetch/LSP paths have stronger permission checks, diagnostics, cancellation, bounds, line-first output windows, spill behavior, and focused tests.
- Provider platform: OpenAI remains the primary complete path, with registry-backed Anthropic, Kimi/Moonshot, and OpenAI-compatible foundations moving toward the 1.0 provider breadth target.
- Extension seams: plugin process protocol pieces, MCP stdio hosting, skill loading, prompt commands, plugin command contributions, and MCP prompts are converging through a unified command/permission/RPC surface.

## Release-Cut Criteria

This line is superseded by the later 0.65, 0.70, 0.75, and 0.80 docs. Do not use the original 0.60 release-cut checklist as current status without fresh validation.

- S113 command-registry validation is now represented by focused command-registry tests and direct headless RPC command-registry smokes.
- The old dirty `ava_tests.app_runtime` marker belonged to the 0.33/0.60 transition and should not be carried forward without fresh failing test output.
- Roadmap and capability re-audits moved through 0.80/0.90 stabilization and are now summarized by the 1.0 backend baseline docs.
- The release-bump decision landed in `1.0.0`; keep this 0.60 checklist as historical evidence rather than current runtime guidance.
- Release verification still uses the baseline from `AGENTS.md`: configure/build, CTest, sanitizer build when practical, and `git --no-pager diff --check`.

## Version Ladder To 1.0

- 0.65: provider-native hardening, Anthropic native coverage, Kimi/Moonshot/OpenAI-compatible validation, provider-switch safety, and provider retry/idempotency decisions.
- 0.70: reasoning and model lifecycle closeout, including reasoning events, reasoning controls, session entries, native replay, and hardened mid-session model switching.
- 0.75: extension foundation alpha, including plugin manifests, explicit enablement, versioned process handshake, extension-scoped permissions/audit, plugin commands and prompt/skill resources, and MCP tools/prompts through bounded registry paths.
- 0.80: extension API stabilization. Authoring docs, sample coverage, compatibility policy, minimal plugin/MCP golden tests, focused audit/failure coverage, and the then-current MCP resource deferral decision landed there; read-style MCP resources later landed behind `mcp.resource.read`.
- 0.90: v1 release-candidate evidence ledger, including protocol freeze, capability re-audit, full verification, live provider smokes, and final runtime-version bump decision.
- 1.0: backend MVP baseline once required provider, reasoning, RPC, session, tool, permission, plugin, MCP, docs, and verification criteria were complete.

## Not 1.0 Yet

0.60 did not declare Backend 1.0/MVP complete. Later version docs resolved or explicitly deferred the 1.0 blockers, with Anthropic/Moonshot/OpenRouter-compatible live smokes kept as post-1.0 provider-breadth validation.
